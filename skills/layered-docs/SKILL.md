# 読む深さを選べる文書を作る

読者が見出し、要点、詳細のどこで読むのをやめても、その深さに応じた理解が成立する文書を作る。
形式を統一することではなく、理解・判断・実行に必要な情報へ到達しやすくすることを目的とする。

## 適用範囲と優先順位

- 文書の作成・修正・レビューに適用する。ファイルだけでなく、チャットに出す文書本文やIssue・PR本文も対象とする。
- 短い文書にも原則は適用するが、不要な見出し・要約・階層を増やさない。短いチャット返答やコードだけの変更には文書の型を強制しない。
- 正確さ、重要条件の保持、読者の目的達成を、字数・項目数・表現形式への適合より優先する。
- ユーザーの明示的な指定、必須テンプレート、適用されるプロジェクト規約を尊重し、その範囲で本規範を適用する。

## 作業前に目的と変更範囲を決める

1. 読者、既知の前提、読み終えて判断・実行できるようになることを定める。
2. 作成・修正・レビューのどれかを確認し、対象範囲と文書の用途を定める。
3. 未知の前提を、それに依存する説明より先に置く。概要の結論は冒頭に置いてよいが、未説明の用語だけで結論を述べない。
4. 節ごとの要点を一文で定める。独立した要点が複数ある場合は、節の分割を検討する。
5. 箇条書き・短い段落・表・図・コードブロックを、情報の関係と読者の用途に応じて選ぶ。

この準備を毎回ユーザーへ説明する必要はない。文脈から判断できる事項を確認質問にしない。正確さや安全な実行に不可欠な不明点は、推測で埋めない。

## 上位だけを読んでも誤解しない構造にする

- 見出しだけで、何の話か、主要な結論と流れが分かるようにする。手順・参照文書では、目的の操作や情報を見つけられることも重視する。
- 見出しと箇条書きの第1階層で、主張と判断に必要な理由の要旨が分かるようにする。短い段落を使う場合は、その冒頭文にも同じ役割を持たせる。
- 第2階層以降には、根拠、具体値、例、補足的な例外、識別子などを置く。読まなくても上位の主張が誤りにならないようにする。

結論・適用範囲・実行可否を左右する条件、例外、警告は、主張と同じ階層に含める。下位階層で上位の主張を取り消したり、重要条件を後付けしたりしない。

三つの深さを必ず作る必要はない。短い内容は、見出しと数項目だけで完結させる。

## 見出しは要点か、探すための名前を示す

- 説明・分析・提案の節は要点を含む見出しにする。「mainの保護」より「mainは保護済みだが承認を省略できる人がいる」のように書く。ただし、見出しの断定を本文より強めない。
- 手順・参照の節では、「復旧手順」「設定項目」「前提条件」など、探しやすい名称型の見出しも使う。
- 見出しは全角30字前後を目安に簡潔にする。短縮によって条件を失う場合は、正確さを優先する。
- 本文の見出しは原則 `##` と `###` までにする。既存の必須構成を壊さない。浅い構成にするために、巨大な箇条書きへ押し込まない。

## 箇条書きと短い段落を使い分ける

- 箇条書きの第1階層は1項目1主張とする。理由が必要な主張は、理由の要旨を同じ項目に含め、詳しい根拠を下位に置く。
- 第2階層には根拠・具体値・例を、第3階層にはさらに細かい補足を置く。入れ子は原則3階層までとし、深くなる場合は節の分割や表を検討する。
- 1項目は原則1〜2文とする。3文以上になったら、分割または短い段落への変更を検討する。第1階層の3〜7項目は目安であり、数合わせの水増し・分割はしない。
- 短い段落は、節のリード、概念の説明、連続した因果の説明に使う。1段落1論点、通常2〜4文を目安とし、画面幅で変わる表示行数では判定しない。
- 列挙・選択肢・主張と根拠の対応は箇条書き、順序に意味がある操作は番号付き手順にする。つながった説明を機械的に細切れにしない。

## 事実・解釈・提案を区別し、必要な根拠を残す

- 事実、解釈・仮説、提案、未確認事項を区別する。原因や理由が不明なら不明と書き、説明を整えるために作らない。
- 主張には必要な理由を添える。ただし、原因不明でも重要な観測事実は残す。判断の根拠には、出典・検証条件・結果を必要な範囲で付ける。
- 読者の理解・判断・再現に不要な作業実況や試行錯誤の羅列は書かない。一方、採用理由、重要な代替案と不採用理由、検証条件・結果、未解決事項は、文書の用途に応じて残す。
- 進捗資料や引き継ぎでは、現状・未完了・次の行動も必要な情報として残す。書き手の作業履歴と、読者に必要な状態情報を混同しない。
- 根拠のない「すべて」「だけ」「必ず」「多く」などを要約や見出しで追加しない。未確認を確認済み、提案を決定事項として書かない。

## 用語・識別子・数・参照を一貫させる

- 想定読者が知らない用語は、初出時または直前に短く説明する。「用語：説明」を使ってよいが、既知の用語まで一律に定義しない。
- 意味を推測できないID、番号、リソース名には、役割の一言を添える。正確な識別子やコマンドは初出から必要な場所に置き、形式上の理由だけで下位へ追いやらない。
- 中心となる語、とくに分類に使う語は、一つの意味に固定する。意味が分かれる場合は別の名称を使う。
- 「4種類」のような列挙の件数は、同じ節の一覧と対応させる。統計値・測定値には、必要な単位、対象範囲、時点、出典を示す。
- 節は「末尾」「次の次」ではなく節名で参照する。既存見出しを変える場合は、目次・内部リンク・アンカーへの影響も確認する。

## 表・図・コードは用途に応じて使う

- 複数対象を複数観点で比較する場合や、一覧から値を探す場合は表を検討する。3対象以上・2観点以上を一つの目安とし、2対象でも有効なら表を使う。
- 比較表は1行1対象または条件、1列1観点とする。セルは短い句または原則1文にし、長い説明は表の外へ出す。一つのセルに異なる条件や対象を詰め込まない。
- 一覧表の列は、探す鍵、判断に効く違い、補足の順を出発点にする。時系列・行列・既存書式では、その読み方を優先する。
- 比較する数量は右揃え、文字や識別子は左揃えを基本にし、共通の単位は見出しへ置く。表示用の表では「—」（該当なし）と「未確認」を区別し、0と混同しない。入力・集計用データの空値や数値型は置き換えない。
- 経路・包含・依存・階層が文章より分かりやすくなる場合は図を使う。単純な関係まで図にしない。図だけに重要な結論や条件を持たせない。
- 図の直後に、線・矢印・配置などの意味を必要に応じて1〜3項目で説明する。色だけで意味を区別しない。出力先で読める形式を選ぶ。
- コマンド・設定例はコードブロックに置く。実行場所、前提、入力、期待結果、危険な操作の注意を必要に応じて近接させる。
- 太字は用語の初出や重要な警告・判断点に限定する。箇条書きの第1階層や行全体を一律に太字にしない。

## 文書の用途に応じて構成を選ぶ

以下は候補であり、全節を必須にしない。不要な空節、同内容の反復、短い文書の過剰な分割を避ける。

- 設計書・意思決定記録：目的・制約 → 判断または提案 → 理由・重要な代替案 → 影響・リスク → 未解決事項。
- 手順書：目的・適用条件・危険事項 → 準備 → 操作と期待結果 → 失敗時の分岐・中止条件 → 必要な復旧方法。分岐は判断が必要な手順の位置にも置く。
- README・参照・オンボーディング：ページの目的 → 必要な前提・全体像 → 使い始めるための案内 → 詳細・確認方法。
- 調査メモ：問いと現在の結論 → 観測事実・検証条件と結果 → 解釈・仮説 → 未確認事項・次の確認。
- Issue・PR：目的または変更の要点 → 理由・影響 → 完了条件または検証結果。Issueの完了条件と、PRで実際に確認した結果を混同しない。

長い文書や、冒頭だけで判断してほしい文書には要点を置く。要点は見出しの言い換えではなく、結論・重要条件・必要な行動を短くまとめる。要約の有無を節数だけで決めない。

## 修正は必要な範囲に限定する

- 依頼された変更と、その整合性を保つために必要な範囲を修正する。本規範への適合だけを目的に、無関係な節を全面改稿しない。
- 内容の変更と表現の整理を混同しない。挙動、数値、識別子、適用条件、確度を不用意に変えない。
- 周辺に重大な誤りや危険な記述を見つけた場合は黙って放置せず、範囲外の指摘として報告する。形式の好みだけを追加指摘しない。

## レビューでは問題と最小修正案を示す

- 問題箇所、読者への影響、最小限の修正案を示す。正確さ・安全性・判断の誤りにつながる問題を先に扱う。
- 全文の書き直しを求められていない限り、修正版の全文は出さない。字数や項目数の目安から外れているだけでは欠陥としない。
- 問題を見つけるために問題を作らない。重大な問題がない場合は、その旨を短く述べる。

## 提出前に浅い読みと整合性を確認する

1. 見出しだけで、文書の主題・流れ・主要な結論、または操作や情報の所在が分かるか。
2. 見出しと第1階層、短い段落の冒頭だけで、主張・理由・重要条件が分かるか。下位を読まないと誤解する箇所がないか。
3. 事実・解釈・提案・未確認事項が混ざっていないか。見出しや要約が本文より強い断定になっていないか。
4. 用語・識別子の説明、語の意味、列挙件数、数値の条件、出典、参照先が整合しているか。
5. 長すぎる項目・段落・セル、深すぎる入れ子、過剰な太字、不要な図表や重複がないか。形式合わせの水増しがないか。
6. 文書の用途に必要な根拠、代替案、検証条件、分岐、未解決事項が落ちていないか。未実施の検証を実施済みと書いていないか。
7. 修正依頼では、無関係な改稿や、見出し変更による参照切れを増やしていないか。

自己チェックの実況や「チェック済み」という定型文は出さない。
文書本文の提出を求められたときは本文だけを出す。レビュー依頼ではレビュー結果を出す。ファイル編集タスクでは、必要な変更概要・検証結果・未確認事項の報告まで省略しない。

## 作業に応じて補足を読む

上記の基本規範を適用し、次の補足は該当する作業に必要な場合だけ読む。

- システムの設計や構成を説明する文書では、[設計文書の組み立て方](references/architecture-documents.md)を読む。
- Word、PDF、スライドなどのファイルを作成・更新する場合は、[出力形式と確認](references/output-formats.md)を読む。
