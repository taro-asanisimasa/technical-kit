# 設計文書を読者の判断から組み立てる

この参照は、システムの構造、構成要素の働き、設計上の選択を説明するときに使う。
対象文書に求められる前提や書式を確認し、説明の深さを決める。

## 全体を知るための説明と、対象を調べる説明を分ける

全体を初めて読む人には、対象の目的、外部との接点、主要部分のつながりを先に示す。
個別の名称や設定値は、何のための情報かを理解できる位置へ置く。

詳細文書では、上位の説明を読者が既に読んでいるかを確かめる。
既読を前提にできる場合は、その文書への入口を示し、対象を調べるための対応表から始める。
対応表では、対象固有の条件、構成要素、処理先などを、今回判断したい関係として並べる。
読者の前提を確認できない場合は、対応表を読むための短い説明を補う。

詳細を増やすたびに全体説明を再掲するのではなく、今回新しく分かる関係に説明を使う。
節の順番も、構成要素の名前順ではなく、読者が関係を確かめる順番で決める。

## 図で関係を見せ、表で対応を確かめる

図には、対象のまとまり、境界、経路を表す役割を持たせる。
表には、条件、対象、値、担当範囲などの正確な組合せを示す役割を持たせる。
図と表を併用する場合は同じ名称を使い、どの要素に対応するかを追えるようにする。

図を読むために設定値をすべて覚える必要がある場合は、情報量を減らすか主題を分ける。
表は一覧を埋めるために使わず、列の組合せで何を判断できるかを定める。
図だけで十分な小さな関係や、表だけで探せる対応に、もう一方を一律追加しない。

成立条件や未確定の関係が判断を左右する場合は、本文と図表の近くで分かるようにする。
補足欄や非表示にできる注釈を読まないと、結論が逆になる配置は避ける。

## 設計の説明を確認可能な根拠へ結び付ける

主張を支える資料や観測が、どの対象と条件を示しているかを確認する。
記述された構成、実際に動いている状態、操作で確かめた結果を、同じ確認済みの状態としてまとめない。
参照した根拠の範囲を超えて、別の条件でも同じ挙動になると結論付けない。

根拠は、該当する主張から必要な箇所を探せる形で示す。
読んだ資料をすべて列挙するより、主張を検証するのに役立つ位置を示す。
資料同士で値や説明が食い違う場合は、どの根拠を採ったかと、解消していない点を分ける。
今後採用したい設計を、現在の対応表や確認結果へ混ぜない。

## 冒頭と詳細を別々に読み直す

冒頭だけで、対象と今回の判断材料を見つけられるかを確認する。
詳細では、名称、条件、数値、単位、図表の対応、根拠が揃っているかを確認する。
上位の説明に戻らなければ理解できない箇所には入口を補い、既に説明済みの内容の長い反復は減らす。
